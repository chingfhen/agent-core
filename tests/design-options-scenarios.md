# Design-options acceptance scenarios

These are specifications, not evidence of live agent trials. Use the same
synthetic context for baseline and skill-assisted runs; record model, harness,
skill revision, outputs, and actual actions. Judge whether the comparison
changes or supports the decision, as well as unnecessary activation or work.

| Request or situation | Expected behavior |
| --- | --- |
| Compare ways for a website and assistant to share revisions. | Compare materially different ownership/data flows against the same relevant constraints and converge on a leader. |
| The human favors a distributed design; a simpler approach meets the constraints. | Compare both fairly and recommend the simpler one if supported; explain its tradeoff. |
| Constraints eliminate all but one credible design. | Explain the elimination; do not invent options to fill a quota. |
| A leader depends on unverified host support. | Qualify the recommendation and identify a bounded discriminator; do not claim compatibility. |
| Two leaders remain tied on a consequential unknown. | Identify the smallest useful discriminator rather than present an unranked menu. |
| Implement the approved design, save the decision, or break agreed work into steps. | Do not reopen alternatives or add an approval ceremony solely due to the wording. |
| Write a skill from an approved brief, or review a plan for omissions. | Do not activate an options exercise without an actual request to compare designs. |
| Request more rationale after selecting a design. | Deepen the explanation without reopening the decision absent contrary evidence. |
