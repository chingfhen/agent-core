# Migration — incremental adoption of established workspaces

Read after the Agent Builder root for an explicit request to assess or migrate an existing agent to Agent Builder. Use only the affected module references. Ordinary context use, setup of a new workspace and routine maintenance do not require this reference. Source publication, skill availability, workspace migration and demonstrated behavior are separate outcomes.

## Aim and authority

Compatibility before conformity. Restore the capabilities the human needs; preserve working context and constraints. Full structural adoption is not a prerequisite for ordinary work. A safe no-op, minimal repair, partial adoption or complete consolidation can each be appropriate. New workspaces use the single managed block; legacy sections may remain in established workspaces as long as each route and rule has one authority.

Inspect and recommend before changing workspace guidance or migrating content. Give the human a short proposal identifying functional problems, worthwhile optional changes, affected surfaces, material risks and what will remain unchanged; get one scoped approval (an exact already approved proposal counts). An assessment alone is read-only. Execute approved changes autonomously; ask again only if materially expanding scope, resolving human-owned intent or encountering consequential ownership, confidentiality or destructive-action ambiguity. Ordinary authorized maintenance can still minimally repair affected cues under the root contract; it is not implicit approval to consolidate sections or extract resources. No extra migration task, registry, mandatory second pass or recurring audit.

## Identify the useful scope

- Confirm the actual workspace, canonical AGENTS.md, current session skill availability, applicable policy, existing managed markers and affected resource locators. Inspect the relevant actual resources, not just their names or an index. Publication does not edit workspace guidance. Old skill names are activation cues for Agent Builder, not a reason to load missing skills; preserve any stricter local checks.
- Inspect only relevant guidance and directly affected entry points, indexes, launch recipes or companion docs. Use a bounded stale-cue search when useful; distinguish historical mentions from live instructions. Do not scan unrelated projects, all archives, dependency trees or other workspaces. Confirm path bases, backend/ref, independent owners and existing uncommitted work. Do not infer permission from a path or installed skill.
- Prioritize dead or contradictory live cues, missing actionable utilization guidance, inaccessible required context and duplicated authority that affect real work. Retain compatible existing names, locations, indexes and content; recommend optional consolidation/extraction only when useful. Explicitly distinguish an affected capability that is blocked from optional deferred cleanup; keep unrelated work usable.
- Before an approved edit, reread targets; refuse ambiguous/incomplete/duplicate/nested markers or unsafe paths. Preserve a recoverable pre-edit version of affected guidance and any material being replaced (existing verified version history or a local policy-approved snapshot, especially if untracked or dirty). No implicit Git init, staging, commit, push, backup reconfiguration, external transfer, cleanup or resource relocation. Never reset or overwrite uncommitted human work.

## Handle intentional contract changes

- **Environment:** when relevant to the approved migration scope, preserve existing working external service integrations and non-secret access/setup knowledge. Read environment.md if adopting or repairing this capability; reuse compatible existing locations and guidance, capture only established expectations, and add its utilization cue without duplicating authority. No automatic connection audit, reconfiguration, credential transfer or full migration prerequisite.

- **Python:** where ordinary Python use is governed by a dead mandatory-load cue or missing execution guidance, prioritize repairing it. Read python.md; install its essential actionable utilization fragment in the existing authoritative section or selected managed block. Preserve targeting, compatibility, no-fallback and team/policy safeguards. Direct verified purpose interpreter is the ordinary route; legacy uv run --locked recipes may sync and are not automatically safe. Reconcile directly affected recipes/instructions only where approved. If a legacy workspace has not yet installed the fragment, use root + python.md for the required checks when needed (not a new standing mandatory-load rule); do not execute through an unverified interpreter or fall back. Report the gap and offer a minimal repair rather than demanding full migration.
- **KB:** existing knowledge/ pages are orientation, not a maintained current synthesis; consequential claims need supporting evidence. Clarify this in live retrieval cues when relevant; no blanket rewrite, freeze marker, move or deletion required. Existing inbox files and producers may remain; arrival does not trigger capture, and selected-source capture in place does not drain or delete the inbox. Explain this to the human if they rely on the queue; producer changes, disposition and cleanup require their own applicable approval. Preserve original locators; do not treat inbox as ordinary recall.
- **Tasks/docs/scripts:** existing paths, uppercase indexes and old filenames remain valid. Use current maintenance routing and conventions for new work; no compulsory mode announcement, whole-workspace scan or automatic maintenance. Preserve saved task permission boundaries and actual continuation evidence.

## Verify the approved increment and stop

Check only affected surfaces: readback and scoped diff, intact markers/independent owners, working locators and no superseded duplicate routing for migrated sections. Confirm preserved constraints and supporting detail before removing its old authority. Use a small representative read/use check for materially affected capabilities when feasible and authorized: relevant task or KB discovery without maintenance load; Python direct interpreter probe and compatibility checks when Python was repaired; correct maintenance routing for a relevant cue. Actual fresh-session loading/behavior is stronger than static guidance inspection; report what was observed versus untested rather than require a new session or suite for every change.

Report a compact outcome: repaired, retained/deferred, material blockers/conflicts, checks and limits. If a write fails, preserve safe independent work, retain original constraints until their replacements are verified, and restore only the affected approved changes if necessary without overwriting later edits. Resume by inspecting actual state and remaining approved scope; skip equivalent completed edits. An unresolved prerequisite blocks only dependent work. Do not label a workspace fully migrated when it is merely usable, or insist on further migration once the approved useful outcome is established.

Skill-set rollback is separate from guidance rollback: use authorized canonical manifest/source restoration and selected-harness sync per the operating manual, resolve the exact replacement copy with ownership verification; do not leave competing skill generations as a normal rollback state. No manual pruning or implicit installation changes.
