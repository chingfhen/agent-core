# KB GitHub persistence

Read only for KB maintenance using connector/API remote access; a local checkout uses [filesystem](kb-filesystem.md). Apply root and [KB module](knowledge-base.md). Resolve owner/repository, selected branch/ref and KB directory (repository root allowed); archive and separately configured legacy page locations retain their own exact identities. A connection/search result does not establish write permission, local file access or access to binary originals. Do not guess default branch, scan other repos for a KB, use Drive or temporary storage as fallback. Confirm needed capabilities from exposed contracts and scoped reads, not test writes. Canonical skill and applicable reference must be available for maintenance; read-only recall can work independently. A read-only connector can supply a labeled unsaved draft, not claim persistence.

- Read exact current files at selected ref, use paths/indexes/tree and bounded supported search. Search syntax varies; default-branch indexed search cannot establish absence elsewhere, recent writes may not be indexed. Verify hits via actual ref; use mutation-returned paths/revisions or direct reads. Respect truncation/pagination and disclose material limits. Exclude inbox/archive from routine recall.
- An explicit request to save to selected remote KB authorizes scoped remote writes only when target and mechanism are clear. Explain commit/PR mechanism when consequential; resolve unclear policy before mutation. Respect branch/PR restrictions. No force push, repo creation, changing sharing, bypassing protection, merge or unrelated edits. A proposed PR is not merged canonical state.
- Read current content and use expected blob SHA/revision or branch-head guards where available. Reconcile concurrent edits or stop; preserve unrelated bytes/sections. Write raw UTF-8 Markdown; no rich-document intermediary.
- Prefer a coherent multi-file write for records and affected indexes. Where supported, native Git trees/commits plus guarded non-forced branch update can publish a batch ([GitHub Git trees](https://docs.github.com/en/rest/git/trees), [Git references](https://docs.github.com/en/rest/git/refs)); preserve base tree and verify scoped changes before ref update. Use existing atomic multi-file capability when available rather than inventing tooling. If only single-file mutations exist, track successful paths, finish missing steps on retry, do not duplicate records or overwrite conflicts. Do not assume every connector exposes batch operations.
- Selected originals stay in place; retain exact verified locator and relevant identity/version, report inaccessible local-only archives. Do not assume Git history or remote KB includes originals. Explicit retention/disposition beyond selected-source capture requires exact authorized location and capability; preserve bytes, verify identity/collision safety if copying, do not infer cleanup from capture. Never publish private raw sources for runtime convenience.
- For approved retirement/restoration, verify exact source and vacant destination in managed/ or retired/ at the selected ref. Prefer one guarded tree/commit update reusing original blob SHAs for moves, including index and link repairs. Otherwise save and verify identical destination bytes before guarded removal of the unchanged source. Verify final ref, source absence, destination fidelity and navigation; report partial state. Discard is separately authorized; Git history alone is not a retirement destination. If no safe supported action, report the limitation.
- Verify target ref persistence and affected navigation with reliable mutation result/commit and targeted reads as needed, not redundant whole-repo audits. Report repo/ref, paths, URLs/revisions and whether saved, proposed or incomplete. Do not claim connector compatibility or end-to-end behavioral validation from static checks.
